# 오픈소스 라이선스 비교와 선택 기준

## 1. 주요 프로젝트 사례
| 프로젝트 | 라이선스 | 유형 | 특징 |
|---|---|---|---|
| React (`react/` 에 포함) | MIT | 허용형 | 2017-09 에 BSD+Patents 에서 MIT 로 변경. 특허 조항이 기업 채택의 걸림돌이었기 때문 |
| Kubernetes | Apache-2.0 | 허용형 + 특허 | 명시적 특허 허여, 기여자 라이선스 조항 |
| Linux 커널 | GPL-2.0 | 강한 카피레프트 | 파생물 배포 시 같은 조건으로 소스 공개 |

## 2. 라이선스 비교
| 항목 | MIT | Apache-2.0 | MPL-2.0 | GPL-3.0 |
|---|---|---|---|---|
| 유형 | 허용형 | 허용형 | 약한 카피레프트(파일 단위) | 강한 카피레프트 |
| 상업적 이용·비공개 파생물 | 가능 | 가능 | 가능(수정한 MPL 파일만 공개) | 배포 시 전체 소스 공개 의무 |
| 명시적 특허 허여 | 없음 | 있음 | 있음 | 있음 |
| 고지 의무 | 저작권·라이선스 문구 | + 변경 사항·NOTICE | 파일 단위 고지 | 전체 고지 |
| 길이·단순함 | 매우 짧음 | 길다 | 중간 | 길다 |
| 다른 라이선스와 결합 | 거의 어디든 | GPL-2.0 과는 비호환 | GPL 과 결합 가능 | 허용형을 흡수 가능, 역은 불가 |

## 3. 선택 기준 (질문 순서)
1. **파생물도 계속 공개되게 하고 싶은가?** 예 → GPL-3.0 / MPL-2.0. 아니오 → 허용형.
2. **특허 분쟁 위험이 큰가?** (기업 참여, 알고리즘 특허) 예 → Apache-2.0.
3. **채택 장벽을 최대한 낮추고 싶은가?** 예 → MIT.
4. **의존하는 라이브러리의 라이선스와 충돌하지 않는가?** 아래 5 참고.
5. **기여자에게 부담을 줄 수 있는가?** CLA 가 필요하면 참여가 줄어든다 → DCO(`Signed-off-by`)로 대체 가능.

## 4. 이 프로젝트의 선택: MIT
- 학기 프로젝트라 특허·기업 참여 이슈가 작고, 가장 짧고 이해하기 쉽다.
- 주식 매매 전략 코드는 누구나 가져다 실험할 수 있어도 무방하다.
- 특허 허여가 필요해지면(외부 기업 협업) Apache-2.0 전환을 ADR 로 논의한다. 저작권자가 단독이라 전환은 쉽지만, 이미 받아 간 사본에는 MIT 가 유지된다.

## 5. 의존성 라이선스 점검
제안서의 기술 스택 중 배포 방식에 영향이 있는 것:

| 패키지 | 알려진 라이선스 | 판단 |
|---|---|---|
| pandas, NumPy, scikit-learn, PyTorch | BSD 계열 | MIT 와 호환 |
| Streamlit, yfinance | Apache-2.0 | MIT 와 호환 |
| **backtrader** | **GPL-3.0** | 결합해 배포하면 전체가 GPL-3.0 적용 대상이 될 수 있음 → "자체 구현"을 우선 검토 |

위 표는 작성 시점의 일반적 지식 기준이므로, 의존성을 추가할 때 각 패키지의 `LICENSE` 를 직접 확인하고 `pip-licenses` 등으로 점검한다.
이 문서는 법률 자문이 아니다.
