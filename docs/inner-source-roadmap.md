# Inner Source 도입 로드맵

Inner Source = 오픈소스의 개발 방식(공개 이슈·PR 리뷰·문서화·기여 환영)을 **조직 내부**에 적용하는 것.
코드는 사내에 두되, 팀 경계를 넘어 누구나 읽고 기여할 수 있게 한다.

## 목표
- 팀 간 중복 개발 감소, 코드 재사용 증가
- 병목이 되는 "담당 팀 한 곳"에 의존하지 않고 요청 대신 **기여**로 해결
- 지식이 사람이 아니라 저장소(문서·ADR)에 남음

## 이 저장소를 시범 사례로
이미 갖춘 것: 라이선스·README·[CONTRIBUTING](../CONTRIBUTING.md)·[행동 강령](../CODE_OF_CONDUCT.md), 이슈 템플릿·라벨, [ADR](adr/), Discussions(RFC), Wiki, DORA·스프린트 지표, 이슈 SLA 자동화.
이것을 "Inner Source 프로젝트 표준 키트"로 삼아 다른 저장소에 복제한다.

## 단계별 로드맵
| 단계 | 기간 | 할 일 | 완료 기준 |
|---|---|---|---|
| 0. 준비 | 1~2개월 | 경영진·팀장 후원자 확보, 사내 기본 라이선스·IP 정책 확정, 보안·비밀정보 규칙 | 정책 문서 승인 |
| 1. 시범 | 3~4개월 | 후보 1~2개 프로젝트를 골라 표준 키트 적용, 담당자(Trusted Committer) 지정 | 외부 팀 기여 PR 첫 병합 |
| 2. 확산 | 5~9개월 | 사내 검색 가능한 저장소 카탈로그, 기여 가이드 교육, `good first issue` 운영 | 시범 3개 이상, 타 팀 기여 비율 측정 |
| 3. 정착 | 10개월~ | 성과 지표를 평가·보상에 반영, 우수 기여자 인정, 정책 정기 점검 | 신규 프로젝트가 기본값으로 inner source 시작 |

## 역할
| 역할 | 책임 |
|---|---|
| 후원자 | 예산·우선순위, 팀장 설득 |
| Trusted Committer | 외부 PR 리뷰·병합, 로드맵 관리. 응답 SLA 준수 |
| 기여자 | 이슈 확인 → 소규모 PR. 담당 팀 가이드를 따름 |
| 커뮤니티 매니저 | 카탈로그·교육·사례 공유 |

## 표준 키트 체크리스트
- [ ] LICENSE(사내용 조항 포함) · README · CONTRIBUTING · CODE_OF_CONDUCT
- [ ] 이슈/PR 템플릿, 라벨 체계
- [ ] ADR 폴더와 RFC 절차
- [ ] 이슈 자동응답·SLA 추적 (현재 이 저장소의 워크플로우 재사용)
- [ ] 코드 소유자(`CODEOWNERS`)와 리뷰 규칙

## 측정 지표
| 지표 | 의미 | 수집 |
|---|---|---|
| 외부 팀 기여 PR 수/비율 | 도입 성과 | PR 작성자 소속 기준 |
| 첫 응답 시간 | 기여 경험 | SLA 워크플로우 |
| 기여자 첫 PR 병합까지 시간 | 진입 장벽 | PR 이력 |
| 재사용 횟수 | 중복 개발 감소 | 의존·복제 집계 |
| DORA 4대 지표 | 전달 성능 유지 여부 | `dora.yml` |

## 위험과 대응
| 위험 | 대응 |
|---|---|
| 담당 팀이 외부 PR 리뷰를 부담스러워함 | 리뷰 시간을 업무로 인정, 표준 PR 템플릿으로 품질 확보 |
| 기여가 몇몇 사람에게 쏠림 | 기여를 평가에 반영, `good first issue` 정기 공급 |
| 코드·비밀정보 유출 | 저장소 가시성 정책, 시크릿 스캔, 사내 계정만 접근 |
| 라이선스 오염 | 의존성 라이선스 점검 도입 ([license-comparison](license-comparison.md) §5) |
| 문서가 낡음 | ADR·Wiki 갱신을 PR 체크리스트에 포함 |

## 오픈소스 공개로의 연결
Inner Source 에서 충분히 검증된 프로젝트는 [라이선스 선택 기준](license-comparison.md)에 따라 외부 공개(오픈소스화)를 검토할 수 있다.
