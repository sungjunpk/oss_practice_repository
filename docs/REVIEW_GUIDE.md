# 코드 리뷰 가이드

## 태그

모든 리뷰 코멘트는 태그로 시작한다. 작성자는 태그만 보고 우선순위를 판단할 수 있어야 한다.

| 태그 | 의미 | 머지 전 반영 |
|---|---|---|
| `[MUST]` | 버그, 데이터 손실, 보안, 요구사항 누락, 잘못된 문서 | **필수** |
| `[SHOULD]` | 가독성·구조·테스트 보강 등 강하게 권장 | 권장 (안 하면 이유를 답글로) |
| `[NIT]` | 취향·사소한 표현 | 선택 |
| `[Q]` | 질문 — 의도 확인 | 답변 필수 |

### 좋은 코멘트

- **무엇이** 문제인지 + **왜** 문제인지 + (가능하면) **어떻게** 고칠지.
- 사람이 아닌 코드에 대해 말한다.

```
[MUST] 시작일이 종료일보다 늦으면 빈 DataFrame 이 그대로 저장됩니다.
수집 직후 `if df.empty: raise ValueError(...)` 로 막아 주세요.
```

## 리뷰어 체크리스트

1. PR 제목·커밋이 Conventional Commits 형식인가
2. 연결된 이슈의 완료 조건(DoD)을 만족하는가
3. 본문의 "확인 방법"을 그대로 따라 했을 때 재현되는가
4. 실패 경로(빈 입력, API 오류, 결측치)를 처리하는가
5. 미래 데이터 누수가 없는가 (시계열 분할·피처 생성 시)
6. 비밀값(API 키 등)이 커밋되지 않았는가

## 진행 방식

1. 리뷰어는 코멘트 마지막에 요약을 남긴다: `[MUST] n건, [SHOULD] n건`.
2. 작성자는 반영 커밋을 push 하고, 각 코멘트에 반영 커밋 해시 또는 미반영 이유를 답한다.
3. `[MUST]` 가 모두 해결되면 Approve → Squash merge.
4. 1인 개발 기간에는 GitHub 가 본인 PR 승인을 막으므로 `Comment` 리뷰로 대신하고, 필수 승인 수는 0 으로 둔다. 팀원이 생기면 1 로 올린다.
